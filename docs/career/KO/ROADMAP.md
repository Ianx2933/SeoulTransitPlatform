# SeoulTransitPlatform — Product & Engineering Roadmap

> 기준: 2026년 10월 · Closed Beta 이후 Public Beta 확대를 위한 제품·엔지니어링 계획.  
> 원칙: 기능 수보다 **데이터 신뢰성 → 사용자의 독립적 활용 → 운영 지속가능성**을 우선한다.

## North Star: Public Mobility Data Product

외부 사용자가 지역·노선·시간대별 교통 수요를 탐색하고, 수치의 출처·측정/보정/추정/예측 구분과 분석 조건을 확인하며, 재현 가능한 **근거 문서 또는 데이터 파일**을 확보할 수 있게 한다.

## P0 · 안전·정확성 (Public Beta 확대 이전)

- [ ] 운영 API 키·인증정보 점검 및 필요한 회전, 민감정보 로그 마스킹.
- [ ] Cloud Run/Cloud SQL/Job 서비스 계정 최소 권한 확인. Secret Manager 적용 범위 검증.
- [ ] Cloud SQL 누락 트리거 확인 및 데이터 영향 검사.
- [ ] 원천·집계 간 누락/중복/총량/시간대 배분 검증 자동화, 실패 시 공개 갱신 차단.
- [ ] 원천 데이터의 이용 조건·재배포 가능 범위·출처 표시 확인.
- [ ] OSM 공식 타일 서버 이용 정책 및 표시·캐시·수요 증가 시 대체 경로 점검.

**완료 기준:** 중요한 정합성 검증이 실패한 신규 집계는 공개되지 않고, 접근 키·권한 관련 식별된 주요 위험이 정리되어 있다.

## P1 · 분석 데이터 마트 신뢰성

- [ ] 측정/보정/추정/예측 구분과 데이터 릴리스 버전 식별자를 설계.
- [ ] BigQuery의 **구버전 6개월 적재**를 해결하고 검증된 32개월 데이터로 재구축.
- [ ] PostgreSQL ↔ BigQuery 지표 정의·집계 합계·기간·경계 버전을 대사.
- [ ] 행정동 경계 및 정류장-행정동 매핑의 버전 관리.
- [ ] `fact_od_dong`의 **grain, 키, 시간 단위, 결측·보정값 처리 정책**을 확정하고 구현.
- [ ] 자주 사용하는 집계에 평균·중위·변동폭·표본 수 등 해석에 필요한 통계 추가.

**완료 기준:** 지정된 데이터 릴리스로 서비스/웨어하우스에서 동일한 지표를 재현할 수 있고, 행정동 OD 집계의 관측·보정·추정 근거가 구분된다.

## P2 · 사용자에게 결과를 전달하는 마지막 단계

- [ ] 공통 데이터 사전과 해석 주의사항, 데이터 갱신일·정정 이력 공개.
- [ ] **대표 시나리오 하나** 선정: 예) 선택한 행정동의 특정 기간·시간대 수요 비교.
- [ ] 시민용 근거 문서 1종: HTML/인쇄·PDF, 기간·지표·출처·버전·방법·한계 포함.
- [ ] 연구용 CSV·Parquet 다운로드: 스키마·필터 조건·지표 정의·이용 조건 포함.
- [ ] 외부 이용자와 함께 조회 → 확인 → 문서/다운로드 전체 흐름 테스트.

**완료 기준:** 외부 사용자가 개발자 개입 없이 하나의 검증된 수요 분석을 끝내고 근거 자료를 가져갈 수 있다.

## P3 · 오케스트레이션과 운영 안정화

- [ ] 현재 로컬 Airflow DAG 목록 및 작업 의존성·재시도·Backfill 필요성을 정리.
- [ ] 로컬에서 사용 중인 Airflow를 클라우드에 배포할 방식과 상시 인프라 비용 결정.
- [ ] Airflow vs Cloud Scheduler의 스케줄 소유권을 정하고 **동일 작업의 중복 실행을 방지**.
- [ ] Cloud Run Jobs는 배치 계산 실행기로 유지할지 결정; DAG와 실행 책임 분리.
- [ ] 적재 작업의 멱등성, 재시도, 실패 알림, 체크포인트·과거 기간 재처리 검증.
- [ ] 기존 GCP 예산 알림을 유지하고 실제 서비스별 월별 지출을 확인.
- [ ] GitHub Actions Push/PR CI( pytest / JUnit / Testcontainers / Vitest )의 실패 대응·핵심 품질 테스트 강화.
- [ ] Caffeine의 캐시 적중/미적중, TTL, 데이터 릴리스 변경 시 무효화·다중 인스턴스 동작 점검.

**완료 기준:** 월별 수집 실패의 위치를 확인하고 필요한 단계만 재실행할 수 있으며, 공개 데이터 갱신이 중복·누락 없이 진행된다.

## P4 · 검증된 후속 분석 확장

- [ ] 구간별 재차인원 Fact/집계 뷰: 실제 관측인지 복원/경로 배정에 따른 추정인지 명시.
- [ ] DEM 기반 정류장 지형 분석을 보행 접근 *실측*으로 오해하지 않게 표시.
- [ ] XGBoost: 시계열 홀드아웃, 단순 기준 모델 비교, 구간별 오차 및 불확실성 검증.
- [ ] 실제 외부 활용 사례와 운영 이력 축적 후 Public Beta 확대 판단.

**진행 원칙:** P4는 P0/P1/P2의 핵심 흐름을 지연시키지 않는다. 도메인 효용이 명확한 항목만 우선 개발한다.

## 공개 확대 판정 (Go / No-go)

- **신뢰:** 데이터 출처·버전·추정 여부·중요한 한계를 확인할 수 있는가?
- **안전:** 비밀정보·권한·데이터 제공 조건·지도 타일 이용 정책에 주요 미해결 문제가 없는가?
- **재현성:** 동일 조건 결과를 다시 만들어 검증할 수 있는가?
- **사용자 가치:** 외부 이용자가 최소 한 가지 완결된 조회·보고서/다운로드 흐름을 수행했는가?
- **운영:** 수집 오류를 감지하고 재실행하며 이전 검증 데이터를 안전하게 제공할 수 있는가?

## 범위에서 제외하거나 보류할 일

- 새 언어·지도 엔진·캐시 서버 도입만을 위한 기술 교체
- 모델 검증 없이 예측 기능을 대표 제품으로 홍보하는 일
- Public Beta 전에 구간 부하·고급 분석의 모든 세부 기능을 완성하려는 시도
- 추가 대형 사이드 프로젝트 착수

## 결정이 남은 항목

1. Airflow 배포 형태 및 Cloud Scheduler와의 역할 분리
2. BigQuery 32개월 재적재·검증 수행 단위와 실패 복구 방식
3. 첫 번째 외부 활용 사례의 지표·화면·문서 범위
4. 실제 프로덕션 Caffeine/Cloud Run 응답시간과 클라우드 비용 기준
