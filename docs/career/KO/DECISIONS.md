# SeoulTransitPlatform — Engineering Decision Log

> 기준: 2026년 10월 · 설계 선택과 변경의 **배경·실제 적용·트레이드오프**를 기록한다.  
> 이 문서의 ADR 번호는 정리 순서를 나타내며 실제 도입 날짜는 아니다.

## ADR-01 · Python / Java / JavaScript의 역할 분리

**배경:** 프로젝트 초기에 데이터 처리·서비스 백엔드·웹 프런트엔드를 구현해야 했고, 세 언어를 처음부터 고려했다.  
**선택:** Python은 익숙한 데이터 처리·분석 언어로, Java는 서버 애플리케이션 개발과 성숙한 백엔드 생태계를 고려해, JavaScript는 웹 적합성과 기존 경험을 바탕으로 채택했다. SQL은 관계형·공간 데이터의 조회·변환·집계에 사용.  
**현재 판단:** 목적별 경계는 유지하되 동일한 계산 로직이 Java와 Python에 중복되는지 검토한다.

## ADR-02 · Java 17 → Java 21

**배경:** 외부 API·DB를 기다리는 I/O 중심 서비스의 동시 요청 처리와 장기 유지보수 지원 기간을 고려했다.  
**선택:** Virtual Threads의 정식 지원과 상대적으로 긴 LTS 지원 기간을 근거로 Java 21로 업그레이드.  
**트레이드오프:** Virtual Threads는 I/O 대기가 많은 요청의 자원 효율을 위한 기술이며, 느린 SQL의 실행시간을 직접 개선하지 않는다.  
**현재 판단:** Java 21을 유지한다. 실제 동시성 최적화와 측정 항목은 [ROADMAP](ROADMAP.md)에 둔다.

## ADR-03 · Microsoft SQL Server → PostgreSQL/PostGIS

**배경:** SQL Server에서 **공간 인덱스를 설계했으나** 당시 공간 SQL의 조건·쿼리 구조 때문에 활용되지 않았다. 공간 SQL 및 GIS 처리 요구가 중요했다.  
**선택:** PostgreSQL/PostGIS로 **단순 이전이 아닌 SQL과 공간 데이터 처리 구조 재설계·마이그레이션**을 수행했다. 쿼리 최적화도 함께 진행했다.  
**관찰:** 이전·재설계 후 캐시 의존 부담이 줄어 Caffeine 기반 클라우드 운영이 실용적임을 확인.  
**설계 판단:** SQL Server에도 공간 인덱스가 있으나 당시 쿼리 구조에서는 활용되지 않았다. DBMS 변경과 공간 SQL/데이터 구조 재설계를 함께 수행했다.  
**현재 판단:** 서비스의 공간 분석·조회 엔진으로 PostGIS를 유지한다.

## ADR-04 · 인덱스 우선, 이후 캐싱: 로컬 Redis → GCP Caffeine

**배경:** `district-demand` API가 로컬에서 약 **9.5~12.9초** 걸렸다. 분석 결과 GIST 인덱스 없이 수행되는 공간 조인과, 일반 btree 인덱스를 쓸 수 없는 `LPAD` 정규화 식별자 비교가 원인이었다.
**선택:** 정류장·경계가 바뀔 때마다 재생성해야 하는 정류장-행정동 사전 매핑 테이블 대신, 공간(GIST)·복합·표현식 인덱스를 추가하고 테이블 통계를 갱신했다.
**측정:** 인덱스 적용 후 측정 호출은 **490ms**, 캐시를 비운 cold 호출은 **1초 미만**, **최선 cold 호출은 약 192ms**였다. 로컬 단일 머신 측정이며, 192ms는 최선값이지 p50/p95가 아니다.
**캐시:** 로컬 실행에서는 Redis가 반복 요청을 캐시한다. 인덱스 적용 후 캐시 적중 없이도 DB 경로가 1초 미만이므로, 클라우드에서는 최소 사양도 DB 비용의 약 3배인 공유 Redis 대신 애플리케이션 내장 **Caffeine** 캐시를 사용한다.
**트레이드오프:** Caffeine은 인스턴스별 로컬 캐시라 인스턴스 간에 공유되지 않는다. 현재 트래픽에서는 허용 가능하며, 캐시 제공자는 설정으로 바꿀 수 있다.
**현재 판단:** 인덱스 기반 쿼리 구조와 클라우드 Caffeine을 유지한다. Cloud Run 운영 환경의 응답시간 측정은 [ROADMAP](ROADMAP.md)에 둔다.

## ADR-05 · BigQuery 분석 웨어하우스 도입

**배경:** 교통 데이터 적재 범위가 초기 계획보다 **12개월 확대**되면서 데이터 저장·분석 요구가 커졌다(현재 32개월).  
**선택:** BigQuery 분석 웨어하우스를 별도로 도입. 사용하면서 이 플랫폼에 광범위한 기간·대량 스캔·집계가 필수적이고 BigQuery의 분석 특성과 잘 맞음을 확인했다.  
**역할:** PostgreSQL/PostGIS는 서비스 조회·공간 SQL, BigQuery는 광범위한 분석·재사용 가능한 데이터 마트.  
**현재 범위:** 기초 Star Schema와 초기 6개월분의 분석 데이터가 적재되어 있다. 전체 기간 재적재와 분석 Fact 확대는 [ROADMAP](ROADMAP.md)에 기술했다.  
**현재 판단:** 광범위한 대량 집계에 적합한 별도 분석 계층으로 BigQuery를 유지한다.

## ADR-06 · Spring Boot / Flask / React

**배경:** 웹서비스와 Python 분석 코드를 연결해야 했다.  
**선택:** Java Spring Boot는 서비스 백엔드, Flask는 **React/JavaScript가 호출하는 Python 분석 API**, React는 브라우저 UI에 사용한다.  
**효과:** Python 분석 로직을 Java에서 중복 구현하지 않고 API로 노출 가능.  
**현재 판단:** 서비스 API와 Python 분석 API의 책임을 분리하고, 공통 지표 정의는 일관되게 관리한다.

## ADR-07 · React / Vite / Leaflet / 지도 타일

**선택:** React는 웹 UI, Vite는 프런트엔드 개발 서버 및 배포 빌드, Leaflet은 GIS 분석 결과의 지도 렌더링과 상호작용에 사용한다.  
**변경:** 초기 배경지도 타일 제공자로 CARTO를 사용했으나, 이용하던 CARTO 서비스가 유료로 바뀌어 현재는 OpenStreetMap 공식 타일 서버 사용.  
**관찰:** 현 시스템은 대량 지도 객체 렌더링 요구가 없고 상호작용 성능 문제도 발견되지 않았다.  
**현재 판단:** 현 요구에 적합한 Leaflet을 유지하고, OSM 공식 타일 서버의 이용 정책과 출처 표시를 준수한다.

## ADR-08 · Airflow 오케스트레이션

**배경:** 10개 파이프라인 모듈 중 외부 API를 호출하는 모듈은 3개다. 로컬 처리 체인(수집 → OD 보정 → 시간대 추정 → 집계)은 각 단계가 순서대로 끝나야 하므로 작업 의존성, 재시도, 실패 추적, 선택적 재실행, 과거 데이터 재처리가 중요하다.
**선택:** 의존 관계가 있는 로컬 체인에 Airflow를 사용한다. 현재 보정 DAG까지 이전했고 나머지 모듈은 수동 실행한다. 클라우드의 월별 시간대 승하차 로더는 의존성 없는 단일 작업이므로 관리형 Airflow 대신 **Cloud Scheduler + Cloud Run Jobs**로 실행한다.
**트레이드오프:** 관리형 Airflow인 Cloud Composer는 단일 정기 작업을 위해 월 DB 비용의 약 30배가 든다. 향후 배포와 책임 분리는 [ROADMAP](ROADMAP.md)에 정리한다.

## ADR-09 · Parquet / PyArrow / Dask / xarray

- **Parquet:** 대용량 교통 데이터의 효율적 저장·반복 재사용.
- **PyArrow:** Python에서 Parquet 파일 입출력.
- **Dask:** 대량 데이터 처리에서 메모리 부담을 제어하기 위한 분할·지연 계산.
- **xarray:** 공간 좌표와 차원을 가진 다차원 배열을 분석할 때 사용.

**현재 판단:** 파일 형식, 입출력, 다차원 연산, 대용량 계산을 서로 다른 책임으로 활용한다.

## ADR-10 · GDAL/OGR / Rasterio / Copernicus GLO-30

- **GDAL/OGR:** 래스터·벡터 공간데이터 변환 및 처리.
- **Rasterio:** Python 환경에서 래스터 데이터를 읽고 분석하는 데 활용.
- **Copernicus GLO-30:** 등고선·지형 분석에 활용하는 고도 자료이며, 정류장 고도·경사도 산출에 사용.

**한계:** GLO-30은 건물·식생 영향을 받을 수 있는 표면 고도 자료이므로 보행로 실측 경사라고 표현하지 않는다.

## ADR-11 · Google Cloud Platform 및 배포 서비스

**선택 이유:** 익숙한 GCP 환경에서 관리형·서버리스 서비스를 이용해 인프라 운영 부담을 줄이고 비용을 관리한다. **결제 예산 알림은 설정**되어 있다.
**서비스 선택:** Cloud Run은 초기부터 서버리스 컨테이너 환경을 목표로 선택; Cloud SQL은 PostgreSQL 운영; Firebase Hosting은 React 호스팅; Secret Manager는 운영 비밀정보 보호. Cloud Scheduler·Cloud Run Jobs는 정기 배치 실행에 활용.  
**현재 판단:** 관리형 서비스와 서버리스 배포를 유지하며, 예산 모니터링·접근 권한·비밀정보 취급을 운영 원칙으로 둔다. `.gitignore`와 Secret Manager의 역할은 구분한다.

## ADR-12 · Git/GitHub, Docker, GitHub Actions, 테스트

**배경:** 형상관리, 컨테이너 실행, 다양한 언어 계층의 테스트가 필요했다.  
**선택:** Git/GitHub로 버전 관리, Docker로 컨테이너 실행 환경을 구성했다. GitHub Actions의 Push/PR 기반 CI에서 **pytest, JUnit, Testcontainers, Vitest가 자동 실행**된다.  
**현재 판단:** 애플리케이션 및 데이터 처리 변경에 대한 자동 테스트를 유지한다. CI와 CD(자동 배포)는 구분한다.

## ADR-13 · XGBoost 예측

**역할:** 미래 교통 수요를 탐색하기 위한 예측 모델.  
**설계 방향:** 예측 수요는 관측·보정·추정 수요와 구분하여 제시한다. 예측 평가와 불확실성 설명의 고도화는 [ROADMAP](ROADMAP.md)에 둔다.

## 설계 결정 기록 원칙

- **선택 의도**와 **측정된 성과**를 분리한다.
- 완료된 구현, 로컬 실험, 운영 중, 미래 계획을 혼동하지 않는다.
- 마이그레이션의 성능 효과는 쿼리/인덱스 재설계의 기여와 구분하여 설명한다.
- 향후 변경 시 기존 ADR에 대한 후속 결정을 추가하되 과거의 선택 이유를 사후 수정하지 않는다.
