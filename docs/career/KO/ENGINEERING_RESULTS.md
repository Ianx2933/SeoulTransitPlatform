## 2. 대표 실적별 근거 정리

### ER-01 · 32개월 데이터 재구축

- **문제:** 장기간 교통 수요 데이터를 동일 기준으로 분석하려면 누락·집계 오류·시간대 배분 오류 등을 점검해야 했다.
- **수행:** **32개월 약 3,000만 행**의 시간대별 승하차 데이터를 재구축했다. 원천 API는 정류장 방문 단위로 행을 반환하는데, 로더가 같은 월·키를 합산하지 않고 덮어써서 2024-01 승차량이 **4,518,304명(3.6%)** 과소집계되었다(행 수는 그대로). 로더가 한 달 전체를 합산한 뒤 적재하도록 수정했다. 6개월분의 공휴일 날짜 오류, 합이 1.105인 대체 시간대 비율, 승객을 누락시키던 0 비율 프로필도 수정했다.
- **검증:** 재구축 후 OD 키 514,499개가 원천과 일치(누락 0, 초과 0)했고, OD 키별 일 승객 수가 보존(1e-07 기준 불일치 0)되었으며, 일 OD 승객 5,345,649명 중 시간대에 배분되지 않은 승객은 0명, 추정기 재실행 시 전체 행 SHA-256이 동일했다. `validate_rebuild.py`가 이 검사들을 실행하고 실패 시 비정상 종료한다.
- **범위:** 2024년 1월~2026년 8월(32개월, 약 3,000만 행).
- **의미:** 장기간 교통 원천 데이터를 정제·재구축해 분석 가능한 형태로 제공할 기반을 마련했다.

### ER-02 · 공간 DB 마이그레이션

- **문제:** SQL Server에서 공간 인덱스를 설계했지만 당시 공간 쿼리의 조건/구조로 인해 인덱스가 활용되지 않았다.
- **수행:** PostgreSQL/PostGIS로 이전하면서 SQL과 공간 데이터 처리 로직을 재설계하고 쿼리를 최적화.
- **확인된 결과:** 마이그레이션 수행, 서비스용 공간 분석/조회 구현, 이전 이후 캐시 의존 부담 감소 및 클라우드 Caffeine 운영 가능성을 확인.
- **의미:** 공간 DB의 교체만이 아니라 공간 SQL 및 데이터 처리 구조를 재설계한 경험이다.

### ER-03 · district-demand 쿼리 최적화

- **문제:** `district-demand` API가 로컬에서 약 **9.5~12.9초** 걸렸다. 공간 조인이 GIST 인덱스 없이 수행되었고, `LPAD`로 정규화한 식별자 비교는 일반 btree 인덱스를 사용할 수 없었다.
- **수행:** GIST·복합·표현식 인덱스를 추가하고 테이블 통계를 갱신했다. 정류장-행정동 사전 매핑 테이블은 검토 후 의도적으로 만들지 않았다.
- **측정:** 인덱스 적용 후 측정 호출 **490ms**, 캐시를 비운 cold 호출 **1초 미만**, **최선 cold 호출 약 192ms**.
- **측정 범위:** 로컬 단일 머신 측정이며, 192ms는 최선값이지 p50/p95가 아니다. Caffeine을 쓰는 Cloud Run 운영 환경의 응답시간은 아직 측정하지 않았다.
- **결과:** 캐시 적중 없이도 DB 경로가 1초 미만이 되어, 클라우드에서는 공유 Redis 인스턴스가 필요하지 않았다.

### ER-04 · 웹 GIS 및 실제 외부 운영

- **수행:** Spring Boot 서비스 API, Flask Python 분석 API, React·Leaflet 지도, GCP 배포; 외부 사용자가 존재하는 Closed Beta 운영.
- **성과:** 개발자 외부의 사용자가 지도와 API를 이용하는 Closed Beta 환경을 구축했다.

### ER-05 · 다층 테스트 및 CI

- **수행:** Python(pytest), Java(JUnit), Docker 기반 통합 테스트(Testcontainers), JS/React(Vitest)의 GitHub Actions Push/PR 트리거 자동 실행 구성.
- **성과:** 코드 변경을 계기로 여러 기술 계층의 테스트와 컨테이너 기반 통합 테스트가 CI에서 실행되도록 구성했다.

### ER-06 · 공간 래스터 및 지형 스냅샷

- **수행:** GDAL/OGR 기반 공간데이터 변환, Rasterio/Python 래스터 분석, Copernicus GLO-30 자료 활용, 정류장별 고도·경사 분석 및 스냅샷 버전 관리.
- **한계:** GLO-30의 표면 고도와 격자 해상도는 보행로의 실제 경사를 정밀하게 나타내지 못할 수 있음. '접근환경 추가 조사 후보' 같은 보수적 용도가 적합.

## 3. 결과 해석과 적용 범위

- **서비스 운영:** 웹 GIS와 공간조회 API는 외부 이용자가 있는 Closed Beta 단계에서 제공한다.
- **웨어하우스와 오케스트레이션:** BigQuery는 초기 6개월 적재 범위, Airflow는 로컬 DAG 실행 범위를 갖는다. 전체 기간 데이터 최신화와 클라우드 오케스트레이션은 [ROADMAP](ROADMAP.md)의 확장 작업이다.
- **지형 데이터 한계:** Copernicus GLO-30 기반 지형 경사는 보행로의 세부 경사를 실측한 값으로 해석하지 않는다.

기술적 선택의 배경은 [DECISIONS](DECISIONS.md), 다음 개발 항목은 [ROADMAP](ROADMAP.md)에 기록한다.
